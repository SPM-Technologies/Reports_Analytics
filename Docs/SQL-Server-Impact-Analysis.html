What changes if the database is Microsoft SQL Server?

Impact on Debezium, Kafka and ClickHouse (and on the application around them) if PostgreSQL were replaced by Microsoft SQL Server, with the possible set-ups, flow charts and a time comparison.

This is an analysis document: nothing in the project was changed. Effort and latency figures are estimates for this project and should be confirmed by a short trial (section 10). Licence statements reflect Microsoft's published edition rules as known at the time of writing; confirm them with Microsoft or your licensing partner before deciding.

1. In one minute

ComponentImpactIn short
KafkaAlmost noneSame broker, same topic pr.patient.report, same message format. One extra internal topic for the SQL Server connector's schema history.
DebeziumMediumA different connector (SQL Server instead of PostgreSQL). It needs SQL Server's built-in Change Data Capture (CDC), which needs SQL Server Agent, which the free Express edition does not have.
ClickHouseMediumThe real-time part (Kafka engine) stays the same. The one-minute sync and the backfill read PostgreSQL directly with postgresql(); ClickHouse has no SQL Server equivalent, so these need an ODBC bridge or a small copy job instead.
The applicationLargeAll SQL written for PostgreSQL (schema, row-level security, JSON, upserts, search) must be rewritten in T-SQL. This is the biggest part of the work, not Debezium or ClickHouse.
LicenceImportantThe rule "open source or freeware only" is met only by SQL Server Express (no CDC, 10 GB per database) or Developer (not allowed for production). Production with CDC means a paid Standard or Enterprise licence.
Bottom line: Kafka and ClickHouse hardly care which database feeds them, because the application publishes one fixed "patient snapshot" message. Debezium cares a little (another connector, CDC must be switched on). The real cost is porting the application's database code and, depending on the edition, the licence.

2. Today's flow (PostgreSQL)

Two things make this portable: the application writes one fixed message (PatientSnapshot) instead of exposing its tables, and ClickHouse consumes that message from Kafka. Only the two database-specific pieces, the Debezium connector and ClickHouse's direct copy (postgresql()), are tied to PostgreSQL.

3.2 Kafka

  • No change to the broker, topics, partitions or retention. Same topic pr.patient.report, same key (patient id), same JSON message, so every consumer works unchanged.
  • One more internal topic (schema history) when the Debezium SQL Server connector is used.
  • With the free-edition set-up (option B below), Kafka can be fed by the application itself instead of Debezium; the topic and message stay the same.

4. Four possible set-ups

A. SQL Server with CDC + Debezium

Closest to today: the outbox is read by the Debezium SQL Server connector; Kafka and ClickHouse unchanged; sync/backfill through ODBC or a copy job.

Needs: Standard or Enterprise (paid) in production; Developer for the POC.

Freshness: seconds.

B. SQL Server Express, no CDC

Free edition. Without SQL Server Agent there is no CDC, so Debezium cannot be used. The application (or a small worker) reads new outbox rows every second or two and sends them to Kafka itself, then deletes them.

Needs: nothing paid; but 10 GB per database and limited memory.

Freshness: 1-5 s.

C. SQL Server, no Kafka

Simplest pipeline: ClickHouse pulls changed rows every minute through ODBC (by ROWVERSION); no Kafka, no Debezium.

Needs: any edition; custom ClickHouse image with the ODBC driver.

Freshness: about 1 minute (like today without the cdc profile).

D. SQL Server only (columnstore)

Drop ClickHouse and Kafka: SQL Server's own column-store indexes speed up reports on the live tables.

Needs: reporting queries rewritten for T-SQL; reports run on the live database again.

Freshness: live. But heavy reports compete with registrations again — the very problem this project solved.

How to read this table:
  • At 1 lakh patients all paths are fast. PostgreSQL and SQL Server behave alike for the existing logic: both are row stores, and SQL Server's only clear advantage is the optional column-store index for summaries.
  • At 1 crore the existing logic slows down by roughly the growth of the data, because counts, totals and deep pages read every matching row of the live tables. Those reads also slow down registrations at the same moment.
  • The report builder grows much more slowly: it reads only the columns a report uses, skips months by partition, and runs on ClickHouse, not on the live database. Choosing SQL Server instead of PostgreSQL does not change its times at all, only how fresh the data is (section 7.1).
  • Assumed times are for one user. With several users running reports at once, the existing logic degrades sooner, because the live database is also busy with registrations.

11. If you already have a licensed SQL Server

Then the licence question of section 6 disappears for production and the choice becomes technical. The recommended set-up is option A (CDC + Debezium + Kafka + ClickHouse): it keeps everything already built on the reporting side and gives seconds-fresh reports.

11.3 Steps (in order)

  1. Trial, 2-3 days (section 10) on SQL Server Developer in Docker: CDC on the outbox, Debezium connector, message compared with today's, delay measured.
  2. Port the database scripts (tables, keys, row-level security with SESSION_CONTEXT, procedures with EXECUTE AS OWNER, JSON custom fields, counters), 5-7 days.
  3. Port the application SQL in the DAOs and the start-up migrator, 4-6 days.
  4. Pipeline: enable CDC on report_outbox only, Debezium SQL Server connector with the same EventRouter and topic; ClickHouse sync and backfill through ODBC or bcp, 4-6 days.
  5. Run all 201 tests again, adjust Docker Compose (SQL Server Developer image with the Agent), update the documents, 4-6 days.
With a licence there is one more possibility: if other hospital systems already live on that SQL Server, the registration data can stay where the rest of the hospital's data is, and Analytics still runs on ClickHouse so that reporting load never reaches the licensed server. A licensed Always On readable secondary could also serve the legacy JSP reports, keeping them off the primary; check with your DBA.

12. Recommendation

  • If the choice is free: keep PostgreSQL. It meets the open-source rule, it is already built and tested, and it gives the lowest delay.
  • If SQL Server is required and a Standard or Enterprise licence exists (section 11): option A (CDC + Debezium). Kafka and ClickHouse stay as they are; most work is porting the application's SQL (about 3.5-5 weeks in total).
  • If SQL Server is required but must be free: option B for real time or C for simplicity, accepting the Express limits (10 GB per database means it cannot hold crore-scale data); in practice a free set-up at that size means PostgreSQL.
  • Avoid option D for large data: it brings back the load of heavy reports on the live database.
Whatever the database, the design choices that make this possible stay the same: one published patient snapshot message, reports on a separate store, and isolation rules in both databases.
