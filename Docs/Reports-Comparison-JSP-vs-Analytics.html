Old JSP reports vs new Analytics

How the two reporting features of the Patient Registration project work, what each can do, and when to use which. Written for business users and for technical staff.

Both run inside the same application, same sign-in, same address: http://localhost:8080/patient-registration/. Nothing was removed: the old reports keep working exactly as before.

1. In one minute

Old reports (JSP)

Two fixed reports: Patient Register (list of patients) and Department Summary (counts and fees per department). You pick a few fixed filters and press Search. They read the live registration database directly, every time.

Good for: the two standard lists, exactly as the hospital has always printed them.

New Analytics (report builder)

A self-service report builder, similar in spirit to Power BI: choose any columns, any filters, any totals, your own formulas, pivot tables, charts and dashboards, and save or share them. It reads a separate copy of the data built for reporting (ClickHouse), which is kept up to date within seconds.

Good for: any question the two fixed reports cannot answer, and large data volumes without slowing down registration.

Key idea: the old reports ask the registration database; with crores of rows, every big report competes with the registration desk. Analytics asks its own copy, designed for counting and summing very many rows, so reports and registration no longer get in each other's way.

3. How the old reports work

Every click on Search, Next page or Excel sends one request that is answered straight from the registration tables.

  1. The page sends the chosen filters (date range, department, gender, category, search text).
  2. The server checks the user may see legacy reports, and only for the hospital currently selected in the header.
  3. ReportDao runs one prepared SQL statement that joins the patient with its contact, visit, department, insurance and medical tables. To show "page 1 of 2,001" it also counts all matching rows.
  4. The database reads (scans) all matching rows to count, sort and total them. With 1 lakh rows this takes well under a second; with crores of rows it takes much longer and uses the same disks, memory and CPU as the registration desk.
  5. Downloads stream the rows through a database cursor straight into the Excel or PDF file, so memory stays small.

4. How Analytics works

The browser holds the report definition (which columns, filters, totals, options). On Run it sends that definition, never SQL, to the reporting API. The server turns it into a safe query on the reporting copy.

  1. The builder lists only the fields this user may see (the hospital's rules can hide, mask or rename fields; see section 8).
  2. The API checks sign-in and the Analytics permission and works out the user's hospitals from the session, never from the request.
  3. QueryBuilder accepts only known fields, operators and functions from the catalogue, turns formulas into SQL through an allow-list, binds every value as a parameter and always adds "only these hospitals". ClickHouse itself refuses any query that does not name the hospitals (second safety net).
  4. ClickHouse is a column store: to total the fee of 1 crore patients it reads only the fee column, compressed, in parallel. That is why big summaries stay fast.
  5. Only the page on screen travels to the browser. Pivot, chart, highlight and drill-down are drawn there; drill-down asks the server again for the patients of the clicked group.

5. How data reaches Analytics

Registration is unchanged: the desk saves into PostgreSQL as before. In the same transaction a small "snapshot" of the patient for reporting (no Aadhaar, masked mobile) is published. Two independent paths copy it into ClickHouse:

  • Real time (optional profile cdc): Debezium reads the database change log (WAL) and sends each snapshot through Kafka; ClickHouse consumes it within seconds. In the test on 16 Oct 2026 a new registration was visible in Analytics in under 5 seconds.
  • One-minute sync (always on): every minute ClickHouse copies patients changed in the last 15 minutes directly from PostgreSQL. If Kafka is not running, data is at most about a minute old.
  • Both write the same version number, so duplicates collapse into one row. The report header shows "Data as of ..." so users always know how fresh the figures are.

7. One question, both ways

Question: "How many female patients did each department register in the last 30 days, and what share of all female patients is that?"

Old reports

  1. Open Department Summary.
  2. Enter the date range by hand, choose gender Female, Search.
  3. The count per department is shown; the share must be calculated in Excel after download.
  4. Next month: enter the dates again.

Analytics

  1. Open the template Department Summary (Report 2) or "+ New report".
  2. Group by Department; Summarise: Patients, and Patients again shown as "% of total".
  3. Filters: Gender is Female; Reg Date in period "Last 30 days".
  4. Run, optionally Chart, then Save. Next month just open it: "last 30 days" moves by itself.
  5. Add it to a dashboard next to other reports if wanted.

10. Speed and load

Measured on this POC machine (7.7 GB RAM, Docker) on 16 Oct 2026, hospital H001 with 1,00,002 patients, second run (warm):

ActionOld JSPAnalytics
Patient register, page 10.23 s0.17 s
Department summary0.44 s0.21 s
Pivot department × gendernot possible0.21 s
Excel of all 1 lakh patients7.0 s (all 14 register columns, 8.4 MB)2.4-5.6 s (5 columns, 3.1 MB)
The Excel files differ in columns, so this row is not a like-for-like comparison. Measured with curl as the hospital administrator on the running containers, second of two runs, no other load.
Read this carefully: at 1 lakh rows both are fast, because PostgreSQL keeps that data in memory. The difference that matters appears at crores of rows: the old reports' scans and counts then take seconds to minutes and compete with registrations on the same database, while ClickHouse reads only the needed columns, compressed and in parallel, on a separate server. Load tests at crore scale were deliberately not run yet (memory limits of this machine; user decision).

11. How fresh is the data?

  • Old reports: always live; a patient saved one second ago is in the report.
  • Analytics: seconds behind with the real-time profile, at most about a minute without it. The "Data as of" time is shown on every report.
  • Changes made directly in the database with SQL scripts (not through the application) reach Analytics through the one-minute sync only if the script also sets updated_at to the current time (and raises row_version) and the sync runs within 15 minutes; otherwise run the backfill. Deleting patients by SQL must also be done in ClickHouse.

13. Limits and open points

  • Old reports cannot show a hospital's own form fields or calculated fields (by design: they stay as they were), but they do follow the hospital's report-field rules and download settings.
  • Analytics pivot: up to 10,000 groups and 50 spread-across columns; a pivot downloads as the flat list of groups.
  • Up to 20 calculated fields per report, formulas up to 2,000 characters, 12 tiles per dashboard.
  • PDF downloads print non-Latin text (e.g. Devanagari) as "???" in both features: Unicode fonts were deliberately left out for now.
  • Crore-scale load tests are still to be done (stage 6, postponed).
