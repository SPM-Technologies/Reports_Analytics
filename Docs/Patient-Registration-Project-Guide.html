Patient Registration System

A multi-hospital patient registration application (Spring MVC + JSP) with a separate, self-service analytics module (ClickHouse + React report builder, fed in real time by Debezium/Kafka), packaged as one WAR and run entirely in Docker. Proof of concept; everything is open source and runs locally.

3.Architecture

A modular monolith in one WAR: the registration side (JSP) and the reporting side (REST API + React) live in separate Maven modules that may not depend on each other; they share only small contracts in pr-shared (signed-in user, hospitals, export writers). The reporting side never reads the registration tables: it reads ClickHouse, which is filled from a published snapshot.

Solid: request and data paths. Dashed: the always-on one-minute sync, the safety net besides the real-time path.

Two Spring contexts

Root — RootConfig

Imports SharedConfig, IdentityConfig (+ SecurityConfig), RegistrationConfig, ReportingConfig. Data sources, JDBC templates, transaction manager (OLTP marked @Primary), services, DAOs, exporters. Static SchemaMigrator runs the SQL scripts before any pool exists.

Web — WebConfig

Spring MVC, JSP resolver, messages, multipart resolver, Jackson (ISO dates), resource handlers for /app/** (unknown routes get index.html). Scans only web/api packages: registration.web, reporting.api, reporting.web, identity.web, identity.api.

WebAppInitializer registers the UTF-8 filter, Spring Security's DelegatingFilterProxy, the dispatcher (with multipart config, 1 MB). The design is Spring-Boot-ready: plain configuration classes and constructor injection, no XML beans.

5.How it works

5.1 Start-up

  1. docker compose up starts pr-postgres and pr-clickhouse (on its first start ClickHouse creates analytics and analytics_test). When both are healthy pr-app starts; when the app is healthy (its sign-in page answers) the one-shot pg-setup creates the test database prtest, the pipeline accounts and the publication; then analytics-setup re-applies the ClickHouse table DDL, copies all patients when ClickHouse is empty and (re)creates the one-minute sync.
  2. SchemaMigrator (a BeanFactoryPostProcessor, so before any pool) connects as the administrator postgres (retrying for about a minute while PostgreSQL starts), creates/updates the application role patientreg_app (no superuser, NOBYPASSRLS) and runs identity-schema.sql → schema.sql → reporting-schema.sql → app-grants.sql. All scripts are idempotent; this is the only migration mechanism.
  3. IdentityBootstrap syncs the built-in roles and creates the super administrator admin if there are no users. With DEMO_DATA=true (.env) DemoDataBootstrap adds the demo hospitals H002/H003 and the demo users if missing. Creating a hospital publishes HospitalCreatedEvent, on which registration seeds its 10 departments. Report templates are upserted by reporting-schema.sql.
  4. The app answers at /patient-registration/; unauthenticated pages redirect to /login, the API answers 401.

5.2 Sign-in and the hospital of each request

  1. Form login (/login), BCrypt passwords; after 5 wrong passwords for one user name from one address that address is paused for 1 minute, doubling with each further block up to 15 minutes (in memory; behind Docker every browser has the same address, so short pauses keep anyone from locking a colleague out for long); refused attempts are audited; generic error messages.
  2. TenantFilter builds a Tenant (user, hospitals with role and permissions, active hospital) and puts it in TenantContext. Roles and access changes take effect on the next request (AccessVersion / session_epoch).
  3. TenantAwareDataSource sets app.hospital_ids and app.user_id on every connection borrowed by the app and clears them on return. PostgreSQL row-level security policies read them: no tenant, no rows.
  4. JSP screens work in the active hospital (chosen in the header); Analytics covers all hospitals where the user has the Analytics permission.

5.3 Registering a patient

  1. GET /patient/new: the form shows the hospital's departments and doctors, its own dropdown values, its own fields in each section, and hides optional standard fields the hospital does not use.
  2. POST /patient/save: PatientValidator checks every standard and custom field (section 13). Internal fields (patientId, hospitalId, registrationNo, status, bmi, deptName) are never bound from the request.
  3. PatientService.register, one transaction: next number from hospital_reg_counter (format H001-REG2026 + 7 digits, per hospital and year, gap-free), insert into patient (with custom_fields JSON) and the 5 child tables (registration visit flagged), then publishSnapshot: the reporting snapshot is written to report_outbox and deleted again in the same transaction (Debezium reads the insert from the WAL). Audit entry PATIENT_REGISTERED.
  4. Redirect to /patient/{id} (another hospital's id answers 404).

5.4 From PostgreSQL to ClickHouse

patientreg.v_patient_report is the published contract: one flat row per patient, no Aadhaar, masked mobile, and only the hospital's own fields that are active, reportable and not hidden. Two paths fill analytics.patient_report: Kafka (seconds) and the refreshable materialized view mv_patient_report_sync (every minute, changes of the last 15 minutes). Both carry version = patient.row_version, so ReplacingMergeTree keeps the newest. When a field's report exposure changes, the affected patients get a new version and are re-copied by the sync.

5.5 Running an Analytics report

  1. The React app loads /api/v1/me, /datasets (the effective catalogue for this user), /reports and /dashboards.
  2. On Run it posts a JSON definition to /api/v1/query. EffectiveCatalog applies the hospitals' field rules and adds own fields (cf_<hospital>_<key>) and shared formulas (sf_<id>); QueryBuilder validates everything against it, compiles formulas (FormulaCompiler, allow-listed functions, bound text), and builds the SQL with FINAL, is_deleted = 0, hospital_id IN (...) and SETTINGS SQL_hospitals='...'.
  3. Paging, sorting, totals, subtotals (ROLLUP), top N + Others, conditions on totals (HAVING), display modes (window functions) and pivot data are computed in ClickHouse; the browser renders table, pivot or chart, highlights and drill-down.

5.6 Downloads

Legacy: ReportService streams from a PostgreSQL cursor into POI SXSSF / OpenPDF. Analytics: ExportService validates and counts first (limits: PDF 50,000, Excel 10 lakh, CSV 20 lakh rows), then streams from ClickHouse. Both go through ExportLimiter (3 at a time, 20 s wait, then 503), need the Export permission, follow each hospital's allowed formats, carry its branding, and are audited.

5.7 Errors

JSP side: GlobalExceptionHandler → error.jsp with a plain message. API side: ApiExceptionHandler → RFC 7807 problem+json (detail, and position for formula errors). Stack traces are only logged.

12.Customisation (stage 5b)

Registration form (Settings)

Own fields: text, long text, number, decimal, date, yes/no, dropdown, multi-select; section, order, required, limits, help text, "Available in Analytics", Normal / Masked (text only) / Hidden. Hide optional standard fields. Own dropdown values. Departments and doctors per hospital.

Report fields (Settings)

Per standard field: Normal, Masked (free text only), Hidden, Administrators only; own label. Applied to lists, filters, sorting, formulas, suggestions and downloads in Analytics, and to the classic Patient Register and Department Summary with their downloads. Derived fields follow their source (age band follows age, month follows date).

Report builder

Calculated fields (formula language, ~45 functions, checked with error position); display as % of total / group, running total, rank, change; subtotals; top N + Others; conditions on totals; pivot; highlighting; drill-down.

Sharing & dashboards

Reports and dashboards private or for the hospital; shared calculated fields; dashboards of up to 12 tiles with filters for all tiles; each tile runs with the viewer's rights.

A new form field is not in reports until an administrator ticks "Available in Analytics". Fields that are not shown in reports never leave the registration database. Full comparison with the old reports: Reports comparison.

13.Validation rules

  • Server-side validation is authoritative: required fields, formats (mobile 10 digits, pincode 6 digits, e-mail), lengths equal to column sizes, numeric ranges (height, weight, fee), date logic (birth not in the future, insurance validity order), dropdown values against the hospital's list, department and doctor of the hospital.
  • Own fields: required (also for forged empty multi-selects), number / whole number, at most 4 decimals and 13 digits, min/max, date 1900-2299, yes/no, allowed options, length, no control characters. Values of unknown or inactive fields are dropped.
  • Settings: field key [a-z][a-z0-9_]{1,29}, unique per hospital; dropdowns 2-100 values without , or ;; min ≤ max within NUMERIC(14,4); masking only for text fields.
  • Formulas: at most 2,000 characters, 400 tokens, nesting 40, 20 per report, 100 shared per hospital; unknown functions and fields refused with their position; stored with field names, shown with labels.
  • Reports: at most 40 columns, 6 group columns, 50 conditions (filter depth 4, 1,000 values per list), page size 1–500 (the screen offers 25–500), offset ≤ 10 lakh, top N ≤ 1,000, pivot 10,000 groups / 50 columns, 3 queries at a time per user; without the download permission a patient list can be paged to row 5,000; saved report definitions ≤ 50,000 characters, dashboards ≤ 20,000 (12 tiles, 10 filters).
  • Settings limits: 100 own fields per hospital, 200 values per dropdown list, 200 doctors per department; field labels must stay unique.
  • Downloads: PDF 50,000 rows, Excel 10 lakh, CSV 20 lakh (Analytics; the classic register PDF/Excel has the same caps); one download per user at a time, 3 in total; export queries end after 300 s.

16.Deployment steps

On any machine with only Docker

  1. Copy the project folder (or the repository).
  2. docker compose up -d --build (or start.bat): PostgreSQL, ClickHouse and the app. The image build compiles everything inside Docker (Maven and Node are not needed on the host).
  3. Real time reporting: docker compose --profile cdc up -d --build (or start.bat cdc) adds Kafka and Debezium and registers the connector.
  4. Demo hospitals and users: created automatically at start because .env has DEMO_DATA=true (H002 City Hospital, H003 Sunrise Hospital and the users of section 11; set it to false for an empty installation).
  5. Sample patients: load-data.bat 100000 1, load-data.bat 20000 2, load-data.bat 10000 3 (or SEED_ROWS=.. SEED_HOSPITAL=.. docker compose --profile seed run --rm seed, then run --rm --no-deps seed-backfill). The exact demo data of this machine (1,00,002 / 20,000 / 10,000) is in backup/patientreg_full_2026-10-16_after-stage5.dump: restore.bat it.
  6. Open http://localhost:8080/patient-registration/ and sign in as admin / Admin@1234.

20.Security & known limitations

  • Hospital isolation in four layers: PostgreSQL RLS, composite keys, permission checks per hospital, forced hospital filter in every ClickHouse query plus the ClickHouse row filter. Another hospital's record answers 404.
  • CSRF tokens on every form and API call; Content-Security-Policy (only own scripts, no framing), Referrer-Policy, SameSite=Lax and HttpOnly cookies; audit log of sign-ins (also refused ones), registrations, exports and every settings, role, formula and dashboard change.
  • No escalation through administration: roles can only be created, given or changed within the administrator's own permissions in that hospital; nobody changes a role they hold; only a super administrator changes a super administrator's hospitals; nobody loses their last hospital.
  • Without the download permission a patient list can be paged only to row 5,000; downloads: one per user at a time, row caps per format (also for the classic register), formats each hospital allows.
  • Only the app port 8080 is published; PostgreSQL, ClickHouse and Kafka Connect REST listen on 127.0.0.1 only; the Debezium password is not shown by its REST API (${env:DBZ_PASSWORD}); the ClickHouse app account cannot lift its limits; the application role cannot write the outbox (only publish_snapshot) nor change or delete templates.
  • No SQL ever comes from the browser; formulas compile through an allow-list with bound values.
  • The reporting copy holds no Aadhaar, masked mobiles, and only reportable own fields.
Known limitations (POC): passwords in plain text in property files and .env; local users only (no SSO); PDF prints non-Latin text as "???" (Unicode fonts skipped); no optimistic locking on concurrent edits of the same setting (last save wins); pivots download flat; crore-scale load tests not done yet; deletes or SQL-script changes made outside the application need a ClickHouse backfill; ClickHouse data lives in a Docker volume (inside Docker Desktop's disk image); database row-level security works per user (all their hospitals), the action-specific checks are in Java; sign-in events carry no hospital, so only super administrators see them in the audit screen; Aadhaar is stored unencrypted and shown on the patient screen to users who may view patients; the first sign-in does not force a new admin password; the app container runs as root; the Java and browser tests need the host tools (tools\, installed Edge); after the cdc profile was used once, its replication slot stays: if Kafka will not be used again, drop it (SELECT pg_drop_replication_slot('pr_outbox_slot')) so it does not keep up to 2 GB of change log.
