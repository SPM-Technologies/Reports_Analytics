How ClickHouse works — explained for relational-database users

What happens to the patient data when it leaves PostgreSQL: how ClickHouse stores it, why it is fast for reports, how updates work, and how it is kept secure. Then each new tool of the project (Docker, Kafka, Debezium, React and others) with an example from this project.

Numbers marked "measured" come from the running system on 18 Oct 2026 (H001 1,00,002 patients, H002 20,000, H003 10,000).

1. Why a second database?

PostgreSQL (OLTP)

OnLine Transaction Processing: many small reads and writes of one patient at a time ("save this registration", "open patient 4711"). Strong at transactions, constraints, joins, updates in place.

ClickHouse (OLAP)

OnLine Analytical Processing: few, large queries over many patients ("patients per department and month for 3 years"). Strong at scanning, counting and summing millions of rows quickly; weak at single-row updates.

The project keeps both: registration writes to PostgreSQL (the source of truth); a copy of the patient data, reshaped for reporting, is kept in ClickHouse; the Analytics screens read only ClickHouse. Heavy reports therefore never slow down the registration desk.

2. Rows vs columns: the one idea to remember

Take 4 patients with 4 columns. A row store (PostgreSQL, SQL Server, Oracle, MySQL) writes all values of one row next to each other. A column store (ClickHouse) writes all values of one column next to each other.

3.2 The bridge: a view that flattens

PostgreSQL publishes one flat row per patient, already joined, through the view patientreg.v_patient_report (the "patient snapshot"). It also adds what reporting needs and removes what it must not see (no Aadhaar, mobile masked):

CREATE VIEW v_patient_report AS
SELECT p.patient_id, p.registration_no, concat_ws(' ', p.first_name, p.last_name) AS patient_name,
       p.gender, c.city, d.dept_name, v.visit_type, v.registration_fee, p.hospital_id,
       p.row_version AS version, ...
FROM patient p JOIN patient_contact c ... JOIN patient_visit v ON ... AND v.registration_visit JOIN department d ...;

4. How a table is stored on disk

The table engine used here is MergeTree (the main ClickHouse engine family). Data is not stored in pages that are updated in place; it is stored in immutable parts.

ClickHouse termClosest RDBMS ideaWhat it is here
Partitiontable partitioningPARTITION BY toYYYYMM(registration_date): one per month. A query for "last month" skips the other partitions completely.
Part(no direct equivalent) a sealed chunk of rowsEvery insert creates a new part, sorted by the sort key. Parts are never changed; they are only merged into bigger parts or dropped.
Mergea bit like VACUUM + reindex, automaticA background thread combines small parts of a partition into bigger ones. During the merge, older versions of a row are discarded (section 7).
Column file(none: rows live in pages)In a "wide" part each column is its own compressed file. Small parts (like most of ours) use the "compact" format: one file, still organised column by column.
Granulea block of rows8,192 rows; the smallest unit ClickHouse reads (section 5).

5. Sort key and the sparse index (instead of a B-tree)

Our table is created with ORDER BY (hospital_id, registration_date, patient_id). Inside every part the rows are physically sorted that way. ClickHouse then keeps a sparse index: not one entry per row (like a PostgreSQL B-tree), but one entry per granule of 8,192 rows.

Two data skipping indexes add help for other filters: idx_dept (the set of departments in each block of granules, so "department = 5" skips blocks without it) and idx_name (an n-gram filter for "name contains ...").

LowCardinality, by example

A city column with 1 lakh rows but only 26 different cities:

stored dictionary (once)stored per row
0 = Pune, 1 = Mumbai, 2 = Nashik, ... 25 = Nagpur0, 0, 1, 0, 2, 25, 0, ... (one byte each)

Instead of "Pune" (4 bytes plus length) 1 lakh times, ClickHouse stores the word once and a 1-byte number per row; the numbers then compress again (LZ4 by default). Grouping by city works on the small numbers. Measured for the whole table: 30.1 MB of data takes 11.4 MB on disk (about 2.6 : 1), and repetitive columns such as gender, city or department compress far better than names.

7. Updates and deletes: versions instead of UPDATE

Parts are never edited, so ClickHouse does not do UPDATE ... WHERE patient_id = 2 the way PostgreSQL does (it can, as a heavy background "mutation", but we do not use it). Instead the table engine is ReplacingMergeTree(version, is_deleted): a change is written as a new row with a higher version.

Example: Neha moves from Pune to Nagpur

In PostgreSQL

UPDATE patient_contact SET city = 'Nagpur'
 WHERE patient_id = 2;
-- row_version of patient 2 goes 1 -> 2

One row, changed in place.

In ClickHouse (just after the change)

patient_idcityversionis_deleted
2Pune10
2Nagpur20

Both rows exist, in different parts.

  • A query with FINAL (SELECT ... FROM patient_report FINAL) shows only the highest version per sort key, i.e. "Nagpur". All our reports use FINAL and is_deleted = 0.
  • Later, a background merge keeps only version 2 and frees the space. Measured today: 2,53,653 stored rows, 1,30,002 visible with FINAL — the rest are old versions waiting for merges (they come from re-copies during development).
  • A delete is a new row with is_deleted = 1 and a higher version.
  • The same change may arrive twice (Kafka and the one-minute sync): both carry version 2, so they collapse into one. This is why duplicates are harmless here.
RDBMS thinking: "the row is updated". ClickHouse thinking: "a newer version of the row is appended; reading with FINAL picks the newest". The version comes from PostgreSQL (patient.row_version), so the newest change always wins, whatever order messages arrive in.

8. How data arrives: tables that are not tables

ClickHouse likes batches: one insert of 10,000 rows is far better than 10,000 inserts of one row (each insert creates a part). Three ClickHouse objects bring the data in:

ObjectRDBMS comparisonWhat it does here
Kafka engine tablea foreign table that reads a queueHolds no data. Reading from it takes the next messages from Kafka (JSON rows) and remembers the position.
Materialized view (normal)an AFTER INSERT trigger, not a stored query resultWhenever a block of messages arrives in the Kafka table, its SELECT runs on that block and inserts the result into patient_report. Bad messages go to pipeline_errors.
Refreshable materialized viewa scheduled job (like a cron + INSERT ... SELECT)Every minute it reads recently changed patients straight from PostgreSQL with the postgresql() table function and appends them. The safety net when Kafka is not running.
BackfillINSERT INTO ... SELECT from a linked serverinfra/clickhouse/pipeline/backfill.sql copies all patients at once (first start, after a restore, after bulk SQL loads).

9. Queries look like SQL — with real numbers

ClickHouse speaks SQL. The differences you will notice are extra functions (toStartOfMonth(), uniqExact(), countIf()) and keywords such as FINAL and SETTINGS.

Example 1: patients by gender in H001

SELECT gender, count() FROM analytics.patient_report FINAL
WHERE is_deleted = 0 AND hospital_id = 1
GROUP BY gender ORDER BY gender;

Female  48811
Male    49201
Other    1990
Measured
ClickHouseread 2,53,200 rows but only the needed columns: 5.6 MB (gender plus the sort-key and version columns that FINAL needs), 125 ms
PostgreSQL (same count on patient)read 3,177 pages of 8 KB = about 25 MB: whole rows, all 24 columns of the patient table

Example 2: department totals since 1 Jan 2026 (partition pruning)

SELECT dept_name, count(), sum(registration_fee) FROM analytics.patient_report FINAL
WHERE is_deleted = 0 AND hospital_id = 1 AND registration_date >= '2026-01-01'
GROUP BY dept_name ORDER BY 2 DESC LIMIT 3;

General Medicine  12449  2492900
Orthopaedics       5238  1557700
Ophthalmology      5191  1557800

Measured: 1,20,236 rows read instead of 2,53,653 (3.6 MB, 75 ms): the monthly partitions before 2026 were skipped without being opened.

At 1 lakh rows PostgreSQL is fast too (under half a second). The gap grows with size: reading 4% of the bytes matters little for 25 MB, a lot for 25 GB. That is the reason for ClickHouse at crore scale (see the reports comparison).

How to read this table:
  • At 1 lakh patients all paths are fast. PostgreSQL and SQL Server behave alike for the existing logic: both are row stores, and SQL Server's only clear advantage is the optional column-store index for summaries.
  • At 1 crore the existing logic slows down by roughly the growth of the data, because counts, totals and deep pages read every matching row of the live tables. Those reads also slow down registrations at the same moment.
  • The report builder grows much more slowly: it reads only the columns a report uses, skips months by partition, and runs on ClickHouse, not on the live database. Choosing SQL Server instead of PostgreSQL does not change its times at all, only how fresh the data is (section 7.1 of the SQL Server document).
  • Assumed times are for one user. With several users running reports at once, the existing logic degrades sooner, because the live database is also busy with registrations.

11. RDBMS habits that change

In PostgreSQL you would...In ClickHouse you...
normalise into many tables and joindenormalise into one wide table (joins exist but are the expensive part)
rely on PRIMARY KEY / UNIQUE / FOREIGN KEYhave none of them enforced: the source system guarantees correctness, ClickHouse collapses versions
UPDATE / DELETE rowsappend a new version (or a delete marker) and read with FINAL
insert row by row inside transactionsinsert in batches; each insert is atomic on its own, there are no multi-table transactions
add an index per filter columnchoose the sort key well, add a few skip indexes, rely on reading only the needed columns
use NULL freelyprefer defaults ('' or 0); Nullable costs space and speed
back it up as the only copytreat it as a rebuildable copy: PostgreSQL is the source; backfill.sql rebuilds it

12. Our table, line by line

CREATE TABLE analytics.patient_report
(
    patient_id          UInt64,                        -- from patient.patient_id
    registration_no     String,
    registration_date   Date,
    patient_name        String,                        -- first + middle + last name
    gender              LowCardinality(String),        -- few values: dictionary encoded
    age_years           UInt8,
    city                LowCardinality(String),
    dept_name           LowCardinality(String),        -- joined in from department
    registration_fee    Decimal(10, 2),                -- from the registration visit
    is_insured          UInt8,                         -- boolean as 0/1
    mobile_masked       String,                        -- 98XXXXXX10, never the full number
    ...                                                -- 33 columns in total
    version             UInt64,                        -- = patient.row_version, highest wins
    is_deleted          UInt8,                         -- 1 = deleted
    source_ts           DateTime64(3, 'Asia/Kolkata'), -- when the change happened in PostgreSQL
    hospital_id         UInt32,                        -- every row belongs to one hospital
    custom_fields       Map(String, String),           -- hospitals' own form fields (reportable ones only)
    ingested_at         DateTime64(3, 'Asia/Kolkata') DEFAULT now64(3),
    INDEX idx_dept dept_id TYPE set(0) GRANULARITY 4,                         -- skip index
    INDEX idx_name lower(patient_name) TYPE ngrambf_v1(3, 65536, 3, 0) GRANULARITY 4   -- "contains" search
)
ENGINE = ReplacingMergeTree(version, is_deleted)       -- newest version wins; deletes are markers
PARTITION BY toYYYYMM(registration_date)               -- one partition per month
ORDER BY (hospital_id, registration_date, patient_id)  -- sort key = sparse index
SETTINGS index_granularity = 8192;                     -- one index entry per 8,192 rows

File: infra/clickhouse/schema/001_patient_report.sql. A hospital's own field "Ward" appears in reports as custom_fields['ward'], only for that hospital's rows.

13. Every new tool, with an example

The original project used Java, Spring MVC, JSP, Tomcat, PostgreSQL, Apache POI and OpenPDF. These tools were added later.

Docker runs everything

What it is: a way to run a program together with everything it needs (operating system libraries, Java, configuration) in an isolated container, started from an image. Like a light virtual machine that starts in seconds.

Why here: anyone with Docker can run the whole system; nothing else needs installing.

Example: the app image is built by Dockerfile in two stages, then run:

FROM maven:3.9.9-eclipse-temurin-21 AS build      # stage 1: compile with Maven
RUN mvn -B -q -DskipTests package
FROM tomcat:11.0.27-jdk21-temurin                 # stage 2: only Tomcat + the WAR
COPY --from=build /src/pr-app/target/patient-registration.war /usr/local/tomcat/webapps/

See it: docker ps lists the running containers (pr-app, pr-postgres, ...).

Docker Compose starts the system

What it is: one file (docker-compose.yml) that describes several containers, their order, settings, ports and storage (volumes), started with one command.

Example:

services:
  postgres:
    image: postgres:18.6
    ports: ["127.0.0.1:5432:5432"]      # reachable only from this computer
    volumes: [pg-data:/var/lib/postgresql]
  app:
    build: .
    depends_on: { postgres: { condition: service_healthy } }   # start after the database is ready

See it: docker compose up -d starts all; docker compose --profile cdc up -d adds Kafka and Debezium (profiles = optional groups).

ClickHouse reporting database

What it is: an open-source column-oriented database for analytics (sections 1–12).

Example: docker exec pr-clickhouse clickhouse-client --user admin --password ChAdmin@1234 -q "SELECT count() FROM analytics.patient_report FINAL" → 130002.

Apache Kafka message queue

What it is: a durable message log. Producers append messages to a topic; consumers read them at their own pace and remember their position (offset). Messages are kept for a time (here 7 days) even after they are read.

RDBMS comparison: an append-only table that many readers can read independently, each with its own bookmark.

Example: topic pr.patient.report, key = patient id (so one patient's changes stay in order), value = the patient snapshot as JSON:

key:   "130009"
value: {"patient_id":130009,"registration_no":"H001-REG20260100003","gender":"Male",
        "city":"Pune","dept_name":"General Medicine","version":1,"is_deleted":0,"hospital_id":1, ...}

See it: docker exec pr-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list

Debezium (on Kafka Connect) change data capture

What it is: a connector that reads a database's own change log (PostgreSQL's write-ahead log) and turns every committed insert, update or delete into a Kafka message. Kafka Connect is the framework that runs such connectors.

Why here: the application does not need to talk to Kafka. It inserts the snapshot into the report_outbox table in the same transaction as the registration (and deletes it again); Debezium sees the insert in the log and publishes it. So a registration and its message are never out of step ("transactional outbox").

Example: infra/debezium/patient-outbox.json

"connector.class": "io.debezium.connector.postgresql.PostgresConnector",
"table.include.list": "patientreg.report_outbox",       -- only the outbox, never patient tables
"slot.name": "pr_outbox_slot",
"database.password": "${env:DBZ_PASSWORD}",             -- not shown by the REST API
"transforms": "outbox"                                  -- EventRouter: payload -> topic pr.patient.report

See it: curl -s http://localhost:8083/connectors/patient-outbox/status → "state":"RUNNING".

PostgreSQL features new to the project

Row-level security: every patient table has a policy so the application sees only rows of the signed-in user's hospitals.

ALTER TABLE patient ENABLE ROW LEVEL SECURITY;  ALTER TABLE patient FORCE ROW LEVEL SECURITY;
CREATE POLICY hospital_isolation ON patient
    USING (hospital_id = ANY ((SELECT patientreg.current_hospitals())::INTEGER[]));
-- the application sets app.hospital_ids = '1,3' on every connection it borrows

Logical decoding (wal_level=logical) lets Debezium read the change log; a publication limits it to the outbox table.

Spring Security sign-in and permissions

What it is: the standard Spring library for authentication (who are you) and authorisation (what may you do), with sessions, password hashing (BCrypt) and CSRF protection.

Example: form login at /login; every form carries <input type="hidden" name="_csrf" value="...">; the API answers 401 when not signed in; a TenantFilter loads the user's hospitals and permissions for every request.

React + TypeScript Analytics screens

What it is: React builds the page in the browser from small components that redraw when their data changes; TypeScript is JavaScript with types, checked before the code runs.

Why here: a report builder with drag-like choices, live tables and charts is much easier as a browser application than as JSP pages that reload on every click. The JSP screens stay; both share one login session.

Example: a filter row component (simplified from pr-ui/src/components/FilterRow.tsx):

export function FilterRow({ row, fields, onChange }: Props) {
  return (
    <select value={row.field} onChange={e => onChange({ ...row, field: e.target.value })}>
      {fields.map(f => <option key={f.name} value={f.name}>{f.label}</option>)}
    </select>
  );
}

Vite front-end build

What it is: the build tool that turns the TypeScript/React source into a few optimised files (index.html, one JavaScript and one CSS file).

Example: npm run build (run automatically by Maven) writes pr-ui/target/classes/META-INF/resources/app/, which is copied into the WAR and served at /patient-registration/app/. For development, npm run dev serves the UI with instant reload.

TanStack Table result grid

What it is: a "headless" table library: it manages columns, rows and sorting state; we draw the HTML ourselves.

Example: useReactTable({ data: result.rows, columns, getCoreRowModel: getCoreRowModel() }) in ResultsTable.tsx; sorting and paging are done by the server, the grid only shows one page.

Apache ECharts charts

What it is: an open-source chart library (bar, line, pie and many more) drawing on a canvas.

Example: a bar chart of patients per department:

chart.setOption({
  xAxis: { type: 'category', data: ['General Medicine', 'Orthopaedics', 'Ophthalmology'] },   // H001, measured
  yAxis: { type: 'value' },
  series: [{ type: 'bar', name: 'Patients', data: [25480, 10632, 10620] }],
});

Maven multi-module + frontend-maven-plugin one build

What it is: the project is split into modules (pr-shared, pr-identity, pr-registration, pr-reporting, pr-ui, pr-app) built by one parent pom.xml; the frontend plugin downloads Node and runs the UI build inside Maven.

Example: mvn install builds the UI, all Java modules and patient-registration.war in one go.

ArchUnit architecture tests

What it is: unit tests about the code's structure.

Example: the build fails if registration code starts using reporting code:

static final ArchRule registrationAndReportingAreIndependent = noClasses()
        .that().resideInAPackage(BASE + "registration..")
        .should().dependOnClassesThat().resideInAPackage(BASE + "reporting..");

Playwright browser tests

What it is: it drives a real browser (here the installed Microsoft Edge) like a user: clicks, types, checks what is shown.

Example: from pr-ui/e2e/hospitals.spec.ts:

test('sees all three hospitals and can compare them', async ({ page }) => {
  await page.goto('app/');

14. Try it yourself (read-only)

# open a ClickHouse prompt
docker exec -it pr-clickhouse clickhouse-client --user admin --password ChAdmin@1234

-- the table's partitions and parts
SELECT partition, count() AS parts, sum(rows) AS rows FROM system.parts
WHERE database = 'analytics' AND table = 'patient_report' AND active GROUP BY partition ORDER BY partition;

-- versions waiting for a merge (stored rows vs visible patients)
SELECT count() FROM analytics.patient_report;          -- all stored versions
SELECT count() FROM analytics.patient_report FINAL;    -- one row per patient

-- one patient's versions
SELECT patient_id, city, version, is_deleted, source_ts FROM analytics.patient_report WHERE patient_id = 2;

-- how much a query read
SELECT read_rows, formatReadableSize(read_bytes), query_duration_ms FROM system.query_log
WHERE type = 'QueryFinish' ORDER BY event_time DESC LIMIT 5;
Do not run OPTIMIZE, ALTER, DELETE or TRUNCATE on the live table while experimenting. If something goes wrong, the table can be rebuilt from PostgreSQL with backfill.sql.
