Patient Registration System

A Spring MVC web application that registers hospital patients (70 fields across 6 tables plus a department master) and produces two reports, each downloadable as Excel or PDF.

Location: D:\Pravin\patient-registration · URL: http://localhost:8080/patient-registration/

Java 21Spring MVC 6.2JSP + JSTL Tomcat 11PostgreSQL 18Apache POI OpenPDF100% open source libraries

1.Overview

The application lets reception staff register a patient in a single form and lets management view and download registration reports. It was built in two phases:

Phase 1 · Application

Registration form with 70 fields in 6 sections, server-side validation, patient detail view, Report 1 (Patient Register) and Report 2 (Department Summary) with Excel and PDF downloads.

Phase 2 · Volume

1 lakh (100,000) realistic patients loaded with every field filled; queries, indexes and downloads tuned and measured at that volume; a cap on concurrent downloads.

3.Architecture

A classic layered web application. The browser talks to Tomcat; Spring's DispatcherServlet routes each request to a controller. The controller calls a service, the service calls a DAO, and the DAO runs SQL against PostgreSQL. Controllers then either render a JSP page or stream a file download.

Request path: browser → DispatcherServlet → controller → service → DAO → HikariCP → PostgreSQL. The response is a JSP page or an Excel/PDF stream.

Two Spring contexts

Root context — AppConfig

DataSource (HikariCP), schema initialiser, JdbcTemplate / NamedParameterJdbcTemplate, transaction manager, services, DAOs, exporters. It scans everything except controllers.

Web context — WebConfig

Spring MVC (@EnableWebMvc), JSP view resolver (/WEB-INF/views/*.jsp), static resources (/resources/**), message source, controllers and the global exception handler.

Both are wired by WebAppInitializer, which replaces the classic web.xml servlet declarations. web.xml still exists, but only for container settings: cookie-only sessions and the error page.

5.How it works

5.1 Application start-up

  1. Tomcat finds WebAppInitializer (a Spring WebApplicationInitializer) inside the WAR and starts the root and web contexts.
  2. AppConfig creates the HikariCP pool from db.properties. If Windows reports the legacy time zone Asia/Calcutta, it is switched to Asia/Kolkata first, because the PostgreSQL container rejects the old name at login (its time-zone database has no Asia/Calcutta alias).
  3. DataSourceInitializer runs schema.sql. Every statement is idempotent (IF NOT EXISTS, ON CONFLICT DO NOTHING), so the script creates the schema on first start and only applies missing pieces afterwards.
  4. WebConfig registers controllers, the JSP view resolver and static resources. The app is then live at /patient-registration/.

5.2 Registering a patient

  1. GET /patient/new: PatientController creates an empty PatientForm (registration and visit dates default to today) and renders patient-form.jsp with dropdown values from Lookups and departments from the database.
  2. In the browser, patient-form.js calculates age from the date of birth and BMI from height and weight. It shows the insurance section only when "has insurance" is ticked and the permanent address only when it differs, and it disables the submit button after the first click.
  3. POST /patient/save: Spring binds the request into PatientForm. Blank strings become null, and the internal fields patientId, registrationNo, status, bmi and deptName are never taken from the request.
  4. PatientValidator checks every rule (section 10). On error the same form is shown again with a message next to each failing field.
  5. PatientService.register() runs in one database transaction:
    • prepare() derives values: default dates, exact age from date of birth, BMI. It also clears the permanent address when it is the same as the current one, and clears the insurance fields when the patient has no insurance.
    • PatientDao.insert() inserts into patient (getting back the new id and registration number), then patient_contact, patient_emergency_contact, patient_insurance, patient_medical_info and patient_visit (flagged registration_visit = TRUE).
    • If any insert fails, all six are rolled back, so no half-saved patients can exist.
  6. The browser is redirected (Post/Redirect/Get) to /patient/{id}, which shows every registration detail (all form fields plus registration number and status; the audit timestamps are not shown) with a "registered successfully" message. Refreshing that page cannot submit the form twice.

5.3 Registration number

Format: REG + year of the registration date + a 7-digit running number from the PostgreSQL sequence reg_no_seq, for example REG20260000001. The number is generated inside the INSERT itself, so it is unique even with many users saving at once. A failed save leaves a gap in the numbers, because sequences are never rolled back.

5.4 Viewing a report

  1. The filter form submits by GET, so every report view is a shareable URL. Filters are bound into ReportFilter; values that cannot be parsed (for example a malformed date) are ignored instead of causing an error.
  2. ReportDao builds the WHERE clause from fixed SQL fragments with bound parameters (no SQL injection is possible) and joins patient, patient_contact, patient_insurance, the registration visit and department.
  3. Report 1 runs a count plus one page of 50 rows (LIMIT/OFFSET). Report 2 runs one grouped query; the grand-total row is computed in Java.

5.5 Downloading Excel or PDF

  1. ReportController asks ExportLimiter for a slot. At most 3 downloads run at once; a 4th waits up to 20 seconds, then gets a "server busy, try again" page.
  2. Only after a slot is granted are the download headers set (Content-Type, Content-Disposition with a timestamped filename such as patient_register_20261015_1530.xlsx).
  3. ReportService.exportRegister() runs in a read-only transaction. That lets the PostgreSQL driver use a server-side cursor (fetch size 2,000), so rows stream from the database instead of loading all 1 lakh into memory.
  4. Each row goes straight to the exporter:
    • Excel: Apache POI's SXSSFWorkbook keeps only 200 rows in memory; the rest go to compressed temp files that are deleted afterwards.
    • PDF: OpenPDF adds the table to the document every 500 rows, which writes those rows and frees them. The header row repeats on every page, and every page has a footer with the report title and page number.

5.6 Errors

GlobalExceptionHandler catches every exception and shows error.jsp with a plain message (page not found, invalid request, server busy, or a generic error). Stack traces and SQL are never shown to the user; server errors are written to the log instead. Container-level errors use the same page via web.xml.

6.ER diagram

All tables live in schema patientreg. patient is the centre. Four detail tables share its primary key (one-to-one), visits are one-to-many, and each visit belongs to one department.

PK = primary key, FK = foreign key, UQ = unique. All patient foreign keys use ON DELETE CASCADE: deleting a patient removes all of their rows.

10.Validation rules

The browser performs quick checks (HTML5 required, maxlength, number and date inputs), but the server is the authority: PatientValidator re-checks everything, so a crafted request cannot store bad data.

RuleFields
RequiredFirst name, last name, gender, date of birth or age, category, mobile, address line 1, city, state, pincode, country, emergency name / relationship / phone, department, doctor, visit type, chief complaint, priority, payment mode. Permanent address when "same as current" is unticked. Provider, policy number and valid-to when insured.
FormatPhones: 10 digits · Pincode: 6 digits · Aadhaar: 12 digits · Email: valid address
Allowed valuesAll 18 dropdowns must hold a value from Lookups (gender, title, state, category, visit type, priority, payment mode, …); department must be an active department
LengthEvery free-text field is checked against its column size (e.g. occupation max 60, chief complaint max 300)
NumbersAge 0–130 · height 30–250 cm · weight 1–400 kg · fee 0–1,00,000 · sum insured 0–10,00,00,000 · fee and sum insured: at most 2 decimals (height and weight are rounded to 1 decimal by the database)
DatesRegistration date not in the future · date of birth not after registration and not more than 130 years earlier · visit date not in the future and not before registration · policy valid-to not before valid-from
Type errorsLetters typed in a number or date field show "Enter a whole number" (age), "Enter a valid number" (decimal fields) or "Enter a valid date" (messages.properties, section 12.2)

13.Deployment steps

The whole system runs in Docker, defined in docker-compose.yml (project patient-registration). To share the project, copy the folder (without tools\, backup\ and target folders); the receiver needs only Docker Desktop.

Prerequisites

  • Docker Desktop (about 4 GB of memory for Docker; everything together uses about 1.6 GB)
  • Ports 8080 (app), 5432 (PostgreSQL), 8123 (ClickHouse) free; 8083 too for the real-time profile
  • Internet only for the first start (images and libraries are downloaded; Maven and npm caches are reused afterwards)

First-time setup

  1. In the project folder run start.bat (or docker compose up -d --build). The first run builds the app image from source (about 3 minutes).
  2. Start-up order is automatic: postgres and clickhouse become healthy → app starts and creates schema patientreg, all tables, indexes and the 10 departments → pg-setup creates the test database prtest, accounts reporting_ro and debezium and the outbox publication → analytics-setup copies all patients into ClickHouse when it is empty and starts the one-minute sync.
  3. Open http://localhost:8080/patient-registration/ (Analytics UI: /patient-registration/app/).
  4. Optional: real-time reports with start.bat cdc (adds Kafka and Debezium; new registrations reach the reports in about 2 seconds instead of up to a minute).
  5. Optional: test data with load-data.bat (1 lakh patients; ClickHouse is reloaded afterwards).

14.Bulk data (Phase 2)

db\load-test-data.sql (run through load-data.bat) generates patients entirely inside PostgreSQL. It is fast (≈ 16 s for 1 lakh), runs in a single transaction (all or nothing), and is deterministic for a given run date (fixed random seed; registration dates are relative to the day it runs). Running it again adds another set of patients rather than replacing them.

What makes the data realistic

  • Every column of all six patient tables is filled. Where a value would not naturally exist, the generator writes meaningful filler ("None known", "Self", "No significant family history").
  • Age mix of children, young adults, adults and seniors; date of birth gives exactly that age; registration dates spread over the last 2 years.
  • Title, marital status and occupation follow age and gender: children are Master/Baby, single, Child/Student; married women are Mrs.; seniors are mostly Retired.
  • 26 Indian cities with matching district, state, pincode prefix and regional language.
  • Departments follow the patient: children mostly Paediatrics, gynaecology only for women 18–45, seniors more often Cardiology / Orthopaedics / Ophthalmology / Neurology. Each department has its own doctors and complaints.
  • All generated patients are insured (so in Report 2 "Insured" equals "Total" for the bulk data). Insurance follows the category: BPL patients have Ayushman Bharat PM-JAY (Government Scheme), STAFF have Corporate cover, and children are covered under a parent's policy.
  • Chronic conditions grow more likely with age and come with matching medications; BMI is calculated from height and weight.
  • Contact details are fictitious; emails use example.com / example.in / mail.example.org.

Verified after loading

Checks run on the 1 lakh generated rows (the 2 hand-entered test patients are excluded; they contain blank optional fields and one test entry of a married 10-year-old): 0 empty or NULL values across all 79 patient-table columns · 100,000 rows in each patient table · 0 violations of the consistency rules (gynaecology only for women, no married minors, age matches date of birth, children's policies held by a parent, BPL → Government Scheme, every patient has exactly one registration visit).

Tomcat memory≈ 700 MB working set after a full Excel and PDF download (streaming keeps memory flat). The process peaked at about 1.6 GB during the 12-simultaneous-download stress test, before the download limit was added.

What made it fast

  • Registration-visit flag. Reports originally found each patient's first visit with a per-row LATERAL … LIMIT 1 lookup (about 0.5–0.7 s per count at 1 lakh). A boolean flag plus a partial unique index turned it into a plain join; the count now takes about 0.12 s.
  • Sort-order index (registration_date DESC, patient_id DESC) for the register's default ordering.
  • Trigram (pg_trgm) GIN indexes for "contains" search on name, registration number and mobile.
  • Streaming downloads (database cursor + POI SXSSF + chunked PDF), so memory stays flat regardless of row count.
  • Download limit. In a test with 12 simultaneous PDF downloads, before the limit every pooled connection was busy and the dashboard failed after 31 s. With the limit, 3 run, the rest get a "busy" page, and screens stay responsive (dashboard 0.26 s).

16.Backup & restore

backup.bat writes a full backup (structure + all data) of schemas patientreg and reporting (saved reports) to backup\patientreg_full_YYYY-MM-DD.dump using pg_dump custom format (compressed). The pg_trgm extension is included, so the file restores into a completely empty database. ClickHouse needs no backup: it is a copy that analytics-setup rebuilds from PostgreSQL.

REM backup (what backup.bat runs)
docker exec pr-postgres pg_dump -U postgres -d postgres -n patientreg -n reporting --extension=pg_trgm -Fc -Z 6 > backup\patientreg_full_2026-10-15.dump

REM restore into a fresh installation, before the app first starts (grants are re-created by pg-setup)
docker compose up -d postgres
docker exec -i pr-postgres pg_restore -U postgres -d postgres --no-owner --no-acl < backup\patientreg_full_2026-10-15.dump
docker compose up -d --build

REM list what a backup contains
docker exec -i pr-postgres pg_restore --list < backup\patientreg_full_2026-10-15.dump
Backup taken 15-Oct-2026: patientreg_full_2026-10-15.dump (17 MB). A test restore into an empty database matched the live data: identical row counts in all 7 tables (100,002 patients), all 21 indexes, the sequence position, and an identical checksum of the patient table.

To restore over the live database instead, stop the app first (docker compose stop app), add --clean --if-exists to pg_restore (this replaces the current data), then empty analytics.patient_report in ClickHouse and run docker compose up analytics-setup so the reports match.

Docker migration backup 15-Oct-2026: migration_2026-10-15_final.dump (17 MB, schemas patientreg + reporting) restored into the new pr-postgres: 100,002 patients in every patient table, 4 saved reports, sequence at 100002.

17.Security & known limitations

Protections in place

  • All SQL uses bound parameters, so SQL injection is not possible. Search wildcards % / _ typed by users are escaped.
  • All user data in pages is HTML-escaped (<c:out> and Spring form tags), which prevents cross-site scripting.
  • Allowed-value, length and range checks on the server; internal fields cannot be set from requests.
  • Friendly error pages; no stack traces or SQL are shown to users.
  • Session cookie is HTTP-only; no session id in URLs.
  • The six-table save is atomic (one transaction).

Known limitations (accepted for now)
