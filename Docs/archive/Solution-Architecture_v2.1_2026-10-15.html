Reporting solution architecture

Self-service, Power BI-style reporting on crores of records, without slowing the live system. Built as a module of the existing Spring MVC + JSP application, deployed as one WAR, and using only open-source software.

Version 2.3 (adds multi-hospital isolation, section 10.1 / D13, and full customisation, section 10.2 / D14). Version 2.1 applied an independent architecture review (summary in section 24). It supersedes Reporting-Architecture-Proposal.html. Status: approved; stages 0–4 built (see section 20).

1.Summary

What users get

A report builder in the browser: choose columns, filter on any column, group, pivot, total, chart, drill down, save and share their own reports, and download exactly what they see as Excel, PDF or CSV. Results appear on the same screen when they press Run.

Why the live system stays fast

Reports read from ClickHouse, a column-store analytics database. It is kept up to date in the background, seconds behind live, by Debezium and Kafka reading PostgreSQL's change log. Report queries never run on the live database.

How it is built

A modular monolith: a Maven multi-module project assembled into one WAR on the same Tomcat. Existing JSP screens keep working; the new React UI and JSON API live in the same WAR, so one login session serves both.

What it avoids

No extra application servers, no cross-site (CORS) setup for the app, no token juggling, no paid licences, and no Spring Boot migration now. The design is upgrade-ready, so that step can come later.

2.Problem, scope & constraints

Problem

In the live product (crores of rows, one PostgreSQL database), reports filter on arbitrary columns. Each such report makes PostgreSQL scan and join large parts of the tables, competing with registrations and other live work for CPU, disk, cache and connections. This POC already showed it at 1 lakh rows: 12 simultaneous PDF downloads took every connection and the dashboard failed after 31 s, until a download limit was added.

Requirements

#Requirement
R1Report load must not affect live activity, whatever the number of report users.
R2Fast filters on any column, plus grouping and totals, over crores of rows.
R3Self-service like Power BI: users shape, save and download their own reports.
R4Results on the front end, on the same screen, when the user presses Run. Downloads start from that screen.
R5A modern UI for the new reports, living with JSP in one project; existing screens keep working.
R6Simple deployment and session handling: one deployable, one Tomcat.
R7Open-source or free software only.
R8Ready for later upgrades (Spring Framework 7 / Spring Boot, scaling out) without redesign.

Constraints

  • No Spring Boot migration in this phase. Everything is built on the current Spring MVC 6.2 / Tomcat 11 / Java 21 setup.
  • Report module completeness comes first (section 9).
  • The POC machine has 7.7 GB RAM, Docker capped at about 3.9 GB and 4 CPUs, and 35 GB free on C: (section 20).

3.Architecture principles

Modular monolith

One deployable with strict internal modules. It is simpler to run than microservices, and any module can still be split out later if it ever needs separate scaling.

Separate reads from writes (CQRS)

PostgreSQL handles transactions; a read-optimised copy in ClickHouse serves reports.

Same origin

JSP pages, the React app and the API share one host and context path, so one session cookie, no CORS and no extra token handling. The optional Superset embedding is the one exception (section 8).

Incremental replacement

New features arrive as new screens beside the old ones (often called the "strangler" pattern). Old JSP screens move only if and when it is worth it; nothing has to be rewritten up front.

Metadata-driven, secure by construction

Reports are built from a catalogue of allowed fields, not hand-coded pages. Every query is generated and secured on the server; the browser never sends SQL.

Upgrade-ready

Constructor injection, one configuration class per module, Boot-style property names, and JSON over HTTP. A later Spring upgrade is then mostly mechanical.

4.Big picture

One WAR, one Tomcat, one session. Registration writes its data and an outbox record in one transaction. Reports (green) read ClickHouse synchronously; Kafka and Debezium (dashed) only keep ClickHouse current. The dotted line is reporting's small metadata pool for saved reports.

Arrows are Maven dependencies. Registration and reporting never depend on each other at compile time or call each other at run time.

Module rules

  • Packages follow modules: com.hospital.patientreg.registration, …reporting, …shared, …app. Today's code lives in …controller/dao/service/report/model/config, so stage 1 renames these packages (an automated IDE refactor). ArchUnit tests then fail the build if one module reaches into another's internals.
  • One configuration class per module (RegistrationConfig, ReportingConfig), listed by WebAppInitializer. Component scans are narrowed to each module's packages.
  • The published contract: registration owns PatientSnapshot v1 (the flattened, minimised outbox payload, section 13.3). It is a documented JSON schema, not a shared Java class; reporting depends only on the schema.
  • Connection pools:
    • OLTP pool (PostgreSQL), owned by registration and marked @Primary.
    • Analytics pool (ClickHouse), owned by reporting.
    • A small reporting-metadata pool (2–3 connections, PostgreSQL schema reporting) for saved reports, shares and dashboards.
    Report queries can never take live-database connections.

8.Sessions & security

  • One session for everything. JSP pages, React and the API share the context path, so the browser sends the same JSESSIONID cookie (already HTTP-only, cookie-only) to all of them. No CORS and no tokens. In production also set Secure and SameSite=Lax.
  • When login is added (out of scope today): Spring Security with session-based form login protects JSP and API alike.
    • JSP forms use the hidden CSRF field.
    • The React app uses a CSRF cookie plus request header, together with Spring Security 6's SPA-specific token request handling (which protects against the BREACH attack). Just exposing the cookie isn't enough.
    • Roles drive datasets, fields and row-level rules (section 10).
  • Identity is the security boundary. Saved and shared reports and row-level security need a real, server-verified user. The POC may use a user selector to demonstrate features, but it must never ship: row-level security based on an identity the browser claims is meaningless.
  • Scaling to more Tomcats later: Spring Session JDBC (Apache 2.0) stores sessions in a database, so no sticky load balancing is needed. Note that it writes to the database on most requests: use a separate database or schema sized for it, not the hot OLTP tables. Session attributes must be serializable.
  • Optional Superset embedding is a separate origin (iframe plus guest-token endpoint, with Superset's CORS and security-header configuration). It is the one exception to the same-origin principle and needs its own security review.

10.Semantic layer, security & caching

The UI never sends SQL. It sends a small report definition (JSON), which the server checks against a dataset catalogue, secures for the current user, and turns into parameterised ClickHouse SQL.

Dataset catalogue (one file per dataset, inside pr-reporting)

{ "id": "patients", "label": "Patients", "table": "patient_report", "version": 3,
  "fields": [
    { "name": "registration_date", "label": "Registration date", "type": "date",   "role": "dimension" },
    { "name": "dept_name",         "label": "Department",        "type": "string", "role": "dimension", "suggest": true },
    { "name": "gender",            "label": "Gender",            "type": "string", "role": "dimension", "suggest": true },
    { "name": "state",             "label": "State",             "type": "string", "role": "dimension", "suggest": true },
    { "name": "age_years",         "label": "Age",               "type": "number", "role": "dimension" },
    { "name": "mobile_masked",     "label": "Mobile",            "type": "string", "role": "dimension", "sensitivity": "masked" },
    { "name": "registration_fee",  "label": "Fee (Rs)",          "type": "money",  "role": "measure", "aggregations": ["sum","avg","min","max"], "scale": 2 },
    { "name": "patients",          "label": "Patients",          "type": "number", "role": "measure", "expression": "count()" }
  ],
  "rowPolicy": "hospital_id IN {user_hospitals:Array(UInt32)} AND dept_id IN {user_depts:Array(UInt16)}" }

Report definition sent by the UI

{ "dataset": "patients",
  "columns": ["dept_name", "gender"],
  "measures": [{ "field": "patients" }, { "field": "registration_fee", "agg": "sum" }],
  "filters": { "and": [ { "field": "registration_date", "op": "relative", "value": "LAST_30_DAYS" },
                        { "field": "state", "op": "in", "value": ["Maharashtra", "Gujarat"] } ] },
  "sort": [{ "field": "patients", "dir": "desc" }],
  "totals": "grand+subtotals", "page": { "size": 100 } }

What the query engine does

  1. Validate: every field, operator and aggregation must exist in the catalogue, so injection and hidden columns are impossible. Text "contains" uses the lower-cased column with escaped % / _ wildcards, as the current ReportDao does.
  2. Secure (D12): add the user's row-policy predicate with the user's values bound as parameters, and apply column masking for their role. This applies to on-screen queries, exports, drill-downs and value suggestions alike. As a backstop, the ClickHouse reporting user has a row policy that reads a per-query setting the app sets, so a bug in the app can't widen access.
  3. Generate SQL:
    • Always FROM patient_report FINAL.
    • GROUP BY with WITH TOTALS for grand totals, and ROLLUP / GROUPING SETS for subtotals.
    • Averages on decimals rounded to the field's scale.
    • Per-query limits through two settings profiles: interactive (short timeout, small result cap) and export (longer timeout, larger cap, streaming).
  4. Cache, safely: the cache key is the final rewritten query (definition + bound row-policy values + masking profile + catalogue version), never the definition alone. Only small aggregate results are cached; detail pages and exports are not. A test guarantees two users with different departments never share an entry. The ClickHouse query cache is used only together with this rule, because it separates entries by ClickHouse user, and all app users share one.
  5. Return JSON: column metadata, rows, totals, next-page token, data-as-of time and query time. The same definition drives downloads.

Adding a column to reporting means adding it to the PatientSnapshot contract, the ClickHouse table and the catalogue file. The UI picks it up automatically.

Row-level rule to confirm: "department" here means the department of the registration visit. Patients seen later in another department would not be visible to that department. Confirm this is the intended rule (decision 5).

10.1 Multi-hospital isolation (D13)

Several hospitals share one installation. Each hospital registers its own patients and must see only its own data; a group user may see the several hospitals they are assigned to. The hospital is the primary security boundary and is enforced at every layer, so one missed filter can't expose another hospital's patients.

Decisions (confirmed 15-Oct-2026)

QuestionDecisionConsequence
Registration numberSeparate series per hospital{HOSPITAL_CODE}-REG{year}{7 digits}, e.g. CITY-REG20260000001; unique on (hospital_id, registration_no)
Same person at two hospitalsSeparate recordsNo cross-hospital matching or merging; no hospital can search another hospital's patients
Multi-hospital usersYes, several hospitals per userA user has a list of allowed hospitals; reports can span them, registration works in one chosen hospital at a time
LoginLocal users for nowUsers and BCrypt password hashes in PostgreSQL; LDAP/AD or an identity server can replace it later without touching the isolation rules
Departments and doctorsSeparate list per hospitaldepartment (and doctors) carry hospital_id; the form shows only the active hospital's lists

Layer 1: data model (PostgreSQL)

  • New master hospital (hospital_id, hospital_code UNIQUE, name, active).
  • hospital_id NOT NULL on patient, all five child tables, department, doctors and the outbox payload.
  • Child tables reference the patient by the composite key (hospital_id, patient_id), and a visit references (hospital_id, dept_id). The database itself rejects a contact, visit or department belonging to a different hospital than the patient, so no "mixed" record can exist.
  • Per-hospital numbering uses a counter table hospital_reg_counter (hospital_id, year, last_no) updated with UPDATE … RETURNING inside the registration transaction. It is gap-free (a failed save rolls it back) and needs no new database object when a hospital is added.

Layer 2: identity and session (Spring Security, D10)

  • Tables app_user (user_id, username, password_hash, active) and app_user_hospital (user_id, hospital_id, role). Roles per hospital: REGISTRATION, REPORTS, HOSPITAL_ADMIN; a GROUP_ADMIN simply has several hospitals.
  • Form login with session and CSRF protection for JSP and React (same origin, same session). Spring Security 6 works with plain Spring MVC and carries over unchanged to Spring Boot.
  • After login the server holds a TenantContext: allowed hospital ids and the active hospital (users with several hospitals switch it in the header; the server checks it is in their list).
  • The hospital is never taken from the browser. hospitalId is a disallowed binding field like patientId; saves always use the active hospital from the session.
  • Every read by id is WHERE patient_id = ? AND hospital_id IN (allowed). Another hospital's patient gives 404 "not found", not 403, so ids can't be probed.

Layer 3: database backstop (PostgreSQL row-level security)

  • The application stops connecting as the superuser postgres (superusers bypass row-level security) and uses a normal role patientreg_app.
  • Each patient table gets ENABLE + FORCE ROW LEVEL SECURITY and a policy: hospital_id = ANY (string_to_array(current_setting('app.hospital_ids', true), ',')::int[]).
  • Every transaction starts with set_config('app.hospital_ids', '<allowed ids>', true) (transaction-local, so a pooled connection never carries one user's hospitals into another request). With the setting missing, the policy matches nothing: the system fails closed.
  • Pipeline accounts are separate: reporting_ro (backfill and sync) gets BYPASSRLS on the published view only; debezium reads only the outbox.

Layer 4: reporting pipeline and ClickHouse

  • hospital_id and hospital_code are added to PatientSnapshot (v2), the Kafka event and analytics.patient_report.
  • ClickHouse sort key becomes (hospital_id, registration_date, patient_id) (immutable columns only, see 13.4), so a hospital's report reads only that hospital's data blocks, which also keeps it fast at crore scale. The table is rebuilt once by backfill.
  • Kafka, Debezium and ClickHouse are internal services; no user connects to them, so no per-hospital topics or databases are needed.

Layer 5: reports (semantic layer, D12)

  • QueryBuilder always adds hospital_id IN {hospitals:Array(UInt32)}, bound from the TenantContext. The report definition from the browser cannot add, change or remove it. It applies to grid, counts, totals, charts, all downloads and the filter value suggestions (which would otherwise reveal other hospitals' doctors or cities).
  • Group users get a "Hospital" field to group, filter and compare by; single-hospital users never see it.
  • Saved reports store the layout only, never data, and belong to a hospital (shared within it); global templates are visible to all. Opening any report always shows the viewer's own allowed data.
  • The legacy JSP reports (ReportDao) and the dashboard counts get the same hospital condition.
  • Cache keys include the bound hospital list (as already required in step 4 above). The ClickHouse backstop row policy described in step 2 also checks the hospital; its exact mechanism is verified when built.

Migration of the current data

  • The existing 100,002 patients, the 10 departments and the saved reports are assigned to a default hospital H001. Existing registration numbers are kept as they are; the H001 counter continues after them.
  • The bulk-data generator spreads new test data over 3–4 hospitals with their own departments and doctors, so isolation is visible and testable.
  • A full backup is taken before the migration; ClickHouse is rebuilt from PostgreSQL afterwards.

Proof: cross-hospital tests (success criterion S8)

Automated tests log in as a hospital A user and try to reach hospital B data by every path: open, edit and print by id, search, both JSP reports and downloads, every API query, export and value suggestion, saved reports, and a forged hospitalId in the form and in the report definition. Every attempt must return nothing or 404. Further tests check that a direct SQL query without the session setting returns zero rows (row-level security fails closed), that registration numbers are independent per hospital, that a child row with another hospital's id is rejected by the database, and that a group user sees exactly the union of their hospitals.

10.2 Everything customisable: fields, calculations, reports (D14)

Requirement (15-Oct-2026): the report builder is mandatory and everything must be customisable from screens, without a developer or a release. The principle: configuration, not code. Every customisation is stored as metadata per hospital, is versioned and audited, and always runs inside the security rules (hospital isolation, masking, permissions), which no customisation can switch off.

Custom fields: from form to report without a release

  • Definitions in custom_field_def (hospital_id, field_key, label, type, section, order, required, rules, options, reportable, sensitivity, version, active). Fields are never physically deleted, only deactivated, so old records and saved reports stay valid.
  • Values in one validated JSONB column patient.custom_fields. The server validates each value against the definition (type, required, range, allowed values), exactly like standard fields; the form is rendered from the definitions.
  • The PatientSnapshot carries custom_fields (reportable fields only, masked or left out according to sensitivity). In ClickHouse they are stored as Map(String, String); the query engine casts on read (number, date, boolean) using the definition. A custom field enabled for reporting appears in the builder immediately, for that hospital only.
  • Turning on reportable for a field that already has data triggers a background backfill of that hospital's rows so old records are included.
  • Promotion: a heavily used custom field can become a real typed column for speed (section 13 field manifest); saved reports keep working because they refer to the field key, not the storage.
  • Standard fields: one field manifest generates the view, the ClickHouse columns, the pipeline column lists and the catalogue, so a developer-added column is a single change.

Calculated fields: a safe formula language

  • Users write formulas such as IF(age_years >= 60, "Senior", "Adult"), registration_fee * 1.18, DAYS_BETWEEN(policy_valid_to, TODAY()), COUNT_IF(is_insured = 1) / COUNT() * 100, MEDIAN(age_years).
  • They are never SQL: the server parses the formula into a syntax tree, checks every function against an allow-list and every field against what the user may see (hospital, role, sensitivity), checks types, and only then translates it to ClickHouse SQL with values bound as parameters. Masked or hidden fields can't be read through a formula.
  • Functions (extensible by adding to the allow-list): arithmetic, rounding; IF, CASE, COALESCE; text (concat, upper, lower, left, contains, length); dates (year, quarter, month, week, day, days/months/years between, today); aggregations (count, count-if, distinct count, sum, sum-if, average, median, percentile, min, max, standard deviation); window calculations (% of total, % of group, running total, rank, difference and growth vs previous period).
  • Guard rails: formula length and nesting limits, the query timeout and result limits of section 14; an editor with field picker, function help, live validation and a preview of the first rows.

Governance of customisation

  • Every change to fields, formulas, lists, roles and shared reports is versioned and written to the audit log (who, when, before/after).
  • Changing a shared calculated field shows which reports use it; incompatible changes create a new version instead of breaking reports.
  • Customisations are per hospital; a group admin can copy a hospital's configuration to another hospital as a starting point.

11.On-screen results (synchronous)

  • Run is one HTTP request; the answer is rendered on the same page. There is no waiting queue, no "check back later" and no email.
  • Downloads reuse the exact on-screen definition (with the same security) and stream rows straight from ClickHouse into the Excel/PDF/CSV writer, so the file starts arriving at once.
  • Kafka is not involved in any request. If the background sync falls behind, reports still answer instantly, and the "data as of" time shows how fresh they are.
  • Response targets are in section 21 and will be measured in the POC.

13.Reporting data platform

13.1 Why a column store

PostgreSQL stores each row together, so a filter on 2 columns still reads whole rows. ClickHouse stores each column separately, compressed, and processes it in large vectorised batches. Its sorted, partitioned parts let it skip blocks that can't match. Reports (few columns, many rows, filters, totals) are exactly this workload.

13.3 Pipeline

  1. Registration saves its six tables as today and, in the same transaction and connection, inserts a PatientSnapshot v1 record into report_outbox, then deletes it.
    • The record is the flattened, minimised report record (section 15).
    • The table stays empty, but both changes are in PostgreSQL's change log.
    • patient.row_version (new column, incremented on every change) is copied into the record as its version.
  2. Debezium (PostgreSQL connector, pgoutput, a publication on the outbox table only) uses its Outbox Event Router to write to Kafka topic patient.report, keyed by patient id so each patient's events stay in order.
    • The router ignores the DELETE.
    • Delete and tombstone records are suppressed in the connector configuration (tombstones.on.delete=false).
    • The payload is emitted as plain JSON (no schema envelope).
    • A heartbeat (heartbeat.interval.ms + heartbeat.action.query) keeps the slot advancing when the outbox is quiet but the rest of the database is busy, which prevents change-log build-up.
    • Debezium connects with a dedicated replication role, not the superuser.
    Alternative: pg_logical_emit_message carries the same record with no outbox table at all; Debezium supports it with pgoutput.
  3. ClickHouse: a Kafka engine table (format JSONEachRow, malformed messages sent to an error stream with kafka_handle_error_mode='stream') and a materialized view insert into patient_report.
  4. Backfill (once, and after any recovery) uses ClickHouse's postgresql() table function to read a flattening view in PostgreSQL, month by month, off-hours. CDC is started before the backfill; version rules (13.5) make the overlap safe.
Writes outside the application bypass the outbox. SQL scripts (including db/load-test-data.sql), manual fixes and cascading deletes all skip it, so after any such change a backfill is required. For the live product, if other systems write these tables, use table-level CDC instead: stream the six tables and flatten inside ClickHouse on a schedule. That catches every writer, but the flat table is minutes rather than seconds behind (decision 3).

13.4 Analytics table

CREATE TABLE patient_report (
    patient_id UInt64, registration_no String, registration_date Date, patient_name String,
    gender LowCardinality(String), age_years UInt8, age_band LowCardinality(String),
    patient_category LowCardinality(String), mobile_masked String,
    city LowCardinality(String), state LowCardinality(String),
    dept_id UInt16, dept_name LowCardinality(String), consulting_doctor LowCardinality(String),
    visit_type LowCardinality(String), payment_mode LowCardinality(String),
    is_insured UInt8, coverage_type LowCardinality(String), registration_fee Decimal(10,2),
    -- ... further report columns (only those approved in section 15)
    version UInt64,                          -- = patient.row_version
    is_deleted UInt8,
    source_ts DateTime64(3, 'Asia/Kolkata'), -- commit time of the change in PostgreSQL
    ingested_at DateTime64(3, 'Asia/Kolkata') DEFAULT now64(3),
    INDEX idx_dept dept_id TYPE set(0) GRANULARITY 4,
    INDEX idx_name lower(patient_name) TYPE ngrambf_v1(3, 65536, 3, 0) GRANULARITY 4
) ENGINE = ReplacingMergeTree(version, is_deleted)
  PARTITION BY toYYYYMM(registration_date)
  ORDER BY (registration_date, patient_id);   -- only columns that never change
  • Why only immutable columns in the key: ReplacingMergeTree treats two rows as the same patient only when the sort key matches, and replaces them only within one partition. If a changeable column (such as department) were in the key, an edit would leave two rows for the patient forever. Department filtering uses the skip index instead.
  • If registration_date is ever corrected, the outbox record carries the old value and the pipeline writes an is_deleted=1 row for the old key.
  • Queries always use FINAL (efficient and parallel in current ClickHouse, with skip indexes honoured). The minimum version is pinned in infra/; is_deleted support needs ClickHouse 23.2 or later.
  • All time columns are declared in IST, so relative filters and "today" match what users expect. The PostgreSQL container runs in UTC and created_at has no time zone, so conversions are explicit.
  • Aggregate tables for dashboards, if added, use refreshable materialized views or FINAL. Insert-triggered aggregate views would double-count replaced rows.

13.5 Correctness rules

TopicRule
Versionpatient.row_version, incremented inside every transaction that changes the patient. CDC and backfill read the same value, so the overlap is harmless and the newest version always wins.
OrderingKafka key = patient id, so one patient's events stay in order. Version-based replacement makes late or duplicate events harmless.
Edits and deletesThe app has no edit or delete path today. When added, they publish PatientSnapshot with a higher version, or is_deleted=1. A department rename is a catalogue change: either re-publish affected patients or look the name up through a ClickHouse dictionary.
Stage-2 incremental copy (before Kafka)Watermark on updated_at with an overlap window of several minutes, not on ids, because concurrent transactions commit out of id order. De-duplication by version absorbs the overlap.
Data as ofThe source commit time (source_ts), plus a heartbeat row that advances even when nobody registers. Lag = now − heartbeat time. Not max(ingested_at), which looks stale at night and fresh during a backfill.
ReconciliationNightly, for closed days only (below the watermark): per-day counts and fee totals in PostgreSQL vs ClickHouse with FINAL. Any difference raises an alert.

14.Guard rails & protecting the live database

Live PostgreSQL

wal_level=logical (one restart). Publication on the outbox only. A heartbeat keeps the slot moving. max_slot_wal_keep_size caps change-log retention (today it is unlimited). If the cap is exceeded the slot is invalidated: recovery is a new slot plus a backfill, with a data gap until it finishes (runbook in section 16). Backfill runs off-hours or from a replica. Legacy JSP reports keep their download limit.

ClickHouse

Two settings profiles (interactive and export) with max_execution_time, max_memory_usage and result caps. Since all app users share one ClickHouse login, ClickHouse quotas act as an overall ceiling. Per-app-user fairness either uses quotas keyed by a per-user quota_key or (simpler) the app limit below.

Application

Per-user concurrent query limit (a semaphore per user, like today's ExportLimiter), a global export limit, row caps per output, the safe cache (section 10), and request timeouts aligned with ClickHouse's.

Freshness

"Data as of" on every report from source commit time and heartbeat; an alert if lag passes a threshold. Reports keep working on slightly older data if the pipeline is down.

15.Patient-data compliance

Patient records are sensitive personal data (for example under India's Digital Personal Data Protection Act, 2023). The reporting copy is kept as small and controlled as possible:

  • Minimise: PatientSnapshot carries only approved report fields.
    • No Aadhaar; mobile masked.
    • Each sensitive field needs explicit approval before it is added: patient name (needed for drill-down lists, but personal data), chief complaint and chronic conditions (free-text health data).
    • Fields that aren't approved stay in PostgreSQL only.
  • Control: role-based datasets and fields, server-side row-level security (D12), a read-only ClickHouse reporting user with a backstop row policy, and Kafka topics limited to pipeline accounts.
  • Retention: Kafka keeps events for a short window (for example 7 days) as a replay buffer. ClickHouse TTL enforces the agreed retention period for report data.
  • Audit: every run and download logged (user, definition, row count, time) and backed up (section 16).
  • Protection: TLS between components and disk encryption in production.

Runbooks to write in the POC

  • Pipeline stopped for longer than the change-log cap (slot invalidated): create a new slot and publication, restart Debezium, backfill the affected period, then reconcile.
  • PostgreSQL restored from backup: replication slots aren't in dumps, so recreate the publication and slot, re-backfill ClickHouse, then reconcile.
  • ClickHouse lost: recreate tables from infra/clickhouse DDL, backfill, then reconcile. Reports show "rebuilding" until done.

18.Spring upgrade readiness (later, separate step)

No framework upgrade happens in this phase. These choices keep it mechanical later:

  • WAR packaging stays. Spring Boot supports JSP with WAR packaging, deployed to Tomcat or run as an executable WAR (not with an executable JAR).
  • Boot defaults already in use: one configuration class per module, constructor injection, Boot-style property names, HikariCP, Jackson and SLF4J. Most hand-written configuration simply disappears.
  • Spring Modulith fit: the module and package layout matches Spring Modulith's conventions, so its module verification can be adopted with Boot. Its event-publication registry is an application-level mechanism, complementary to, not a replacement for, the Debezium CDC outbox.
Risk to plan for: open-source support for Spring Framework 6.2 (this project's version) ended in June 2026, per the official Spring Framework versions wiki. Security fixes now come only through commercial support.
  • Interim option without Boot: upgrade in place to Spring Framework 7. It targets Jakarta EE 11 / Servlet 6.1 on JDK 17+, matching Tomcat 11 and Java 21 here.
  • What changes: Jackson 3 is the new default, but Jackson 2 still works (deprecated) in 7.0. Other breaking changes to check:
    • HttpHeaders is no longer a MultiValueMap.
    • spring-jcl is removed.
    • Suffix-pattern and trailing-slash matching are removed.
    • javax.annotation / javax.inject are dropped.
    • ListenableFuture is removed.
  • The live product's upgrade timeline should account for this.
