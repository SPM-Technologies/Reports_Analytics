Moving reports off the live database

A proposal for scalable, isolated reporting on crores of records, using only open-source software, proven first on the Patient Registration POC.

Status: for discussion. Nothing has been built yet; the POC plan in section 13 is the next step once a direction is agreed.

1.Summary

Problem. Today every report runs as SQL against the same PostgreSQL database that handles registrations and day-to-day work. Report filters on arbitrary columns force PostgreSQL to scan and join large parts of the tables. With crores of rows and many clients pulling reports at once, those scans compete for the same CPU, disk, memory cache and connections as live transactions, so everyday work slows down.

Recommendation. Split reads from writes (an approach known as CQRS):

  1. PostgreSQL stays the system of record. The existing screens and reports keep working unchanged.
  2. Every change is streamed out of PostgreSQL in near real time by reading its change log (change data capture, CDC) with Debezium, through Apache Kafka.
  3. The changes land in ClickHouse, a column-oriented analytics database built for fast filtering and aggregation over billions of rows and many concurrent users.
  4. New reports (and, report by report, the old ones) read from ClickHouse. Heavy downloads become background jobs.

Isolation

Report queries never touch the live database. Its only extra work is writing its normal change log, which it already does, plus one small extra row per registration (section 7).

Speed at scale

Columnar storage reads only the columns a report uses, heavily compressed, and processes them in bulk. Filters on any column are fast without an index for each one.

Low risk

The old flow keeps running. Each report switches to the new store with a setting and switches back the same way. The data is seconds behind live.

Everything proposed is open source (Apache 2.0 or the PostgreSQL licence). The POC can be built in stages on this project; a rough estimate is 8–12 working days, refined in section 13.

2.The problem today

Today: transactional work and reporting share one database and one connection pool.

What the POC already showed (1 lakh patients)

  • With 12 simultaneous PDF downloads, every pooled connection was held by a report. The dashboard waited 31 s and then failed. A download limit (3 at a time) now protects this POC, but it only rations the problem; it doesn't remove it.
  • Reports join 5 tables and count every matching row on each page view. That is fine at 1 lakh (0.1–0.4 s), but this work grows roughly in proportion to row count, so at crores the same pattern means much longer scans, larger sorts that spill to disk, and more cache churn for live traffic.
  • "Contains" search and filters on columns without an index degrade into full scans. Adding an index for every filterable column slows every insert and update on the live system.

4.Why row-store scans hurt, and what a column store changes

Reports are exactly the workload column stores are built for: few columns, many rows, filters, grouping and totals. Live transactions (insert or update one patient) are exactly what PostgreSQL is built for. Using each for its strength is the core of this proposal.

Why ClickHouse over the alternatives

  • Apache Doris / StarRocks (also Apache 2.0, also columnar) handle large multi-table joins better. They are a valid alternative if reports need heavy joins; ClickHouse is chosen for its simple single-binary setup, very wide adoption and documentation, and because we will flatten the data into one wide table anyway (section 8).
  • Apache Druid / Pinot are excellent for real-time event analytics but have more moving parts (multiple node types and deep storage); that is more than this use case needs.
  • A read replica is the simplest isolation step and can be added later for other reasons (high availability). It still scans rows, so it doesn't solve G2/G3 at crores.

6.Recommended architecture

Green = new. The write path is unchanged apart from one outbox insert per registration. Reports read only from ClickHouse; the dashed arrow shows old reports can keep using PostgreSQL until they are switched.

How a change flows

  1. A user registers a patient. The app saves the six tables exactly as today and, in the same transaction, writes one outbox row containing the flattened report record (section 7.2).
  2. PostgreSQL writes the transaction to its change log (WAL), which it already does for crash safety.
  3. Debezium reads the change log through a replication slot. This is a streaming read of the log, not a query on the tables, and it publishes the outbox event to a Kafka topic.
  4. ClickHouse consumes the topic continuously (Kafka table engine) and a materialized view writes each event into patient_report.
  5. The new report pages query ClickHouse. Each page shows "data as of hh:mm:ss" from the latest ingested event. End-to-end delay is typically a few seconds; the POC will measure it.

7.Data pipeline in detail

7.1 Change data capture with Debezium

  • PostgreSQL setting wal_level = logical (one-time change plus restart). Debezium uses the built-in pgoutput plugin, so nothing needs installing inside PostgreSQL.
  • A publication limited to the tables we stream (only the outbox table in the recommended design), and one replication slot.
  • Kafka gives durability and replay: if ClickHouse is down, events wait in Kafka; if Kafka is down, PostgreSQL keeps the change log in the slot until Debezium catches up (with a cap, see section 10).

7.2 Flattening the data: transactional outbox (recommended)

A registration touches six tables. Column stores work best with one wide, pre-joined table, and joining six streamed tables inside ClickHouse at crores is expensive. The outbox pattern solves this at the source:

-- in PatientService.register(), inside the existing transaction, after the six inserts
INSERT INTO report_outbox (aggregate_id, event_type, payload)        -- payload = flattened JSON
VALUES (:patientId, 'PatientRegistered', :json);
DELETE FROM report_outbox WHERE aggregate_id = :patientId;            -- table stays empty;
                                                                       -- the INSERT is still in the WAL
  • The app already holds every field in PatientForm at save time, so building the JSON costs almost nothing.
  • Debezium's Outbox Event Router sends the payload to topic patient.report.
  • The event can carry only the fields reports need, which also keeps sensitive data out (section 11).
  • Future edits and cancellations publish PatientUpdated / PatientDeleted events the same way, with a version number.
Alternative without touching the save code: stream the six tables as they are and rebuild the flat table inside ClickHouse on a schedule (a refreshable materialized view). This means zero application change, but more ClickHouse work, minutes rather than seconds of delay for the flat table, and more data copied. It's a good fallback if changing the live save path is not allowed.

7.3 Initial load (backfill) of existing crores

  1. Create a view v_patient_report in PostgreSQL that produces exactly the outbox JSON's columns (a join of the six tables).
  2. Start CDC first, so nothing is missed from that moment.
  3. Bulk-copy history with ClickHouse's built-in postgresql() table function, month by month, off-hours or from a read replica: 
    INSERT INTO patient_report
SELECT *, 0 AS version, 0 AS is_deleted
FROM postgresql('pg-host:5432', 'postgres', 'v_patient_report', 'reporting_ro', '***', 'patientreg')
WHERE registration_date >= '2024-01-01' AND registration_date < '2024-02-01';
  4. Rows copied twice (by backfill and by CDC) collapse automatically: the table keeps the highest version per patient (section 8).

7.4 Freshness, failures and correctness

  • Lag: shown on every report ("data as of"), and monitored. If ClickHouse falls behind, reports still work, just with older data.
  • Exactly-once in effect: delivery is at-least-once; duplicates are removed by version-based de-duplication.
  • Reconciliation job (nightly): compare per-day counts and fee totals between PostgreSQL and ClickHouse and alert on any difference. During the POC and early rollout this is the proof that both sides agree.

8.Analytics data model (ClickHouse)

CREATE TABLE patient_report
(
    patient_id         UInt64,
    registration_no    String,
    registration_date  Date,
    patient_name       String,
    gender             LowCardinality(String),
    age_years          UInt8,
    age_band           LowCardinality(String),      -- 0-13, 14-24, 25-44, 45-59, 60+
    patient_category   LowCardinality(String),
    mobile_masked      String,                      -- e.g. 98XXXXXX10, no Aadhaar at all
    city               LowCardinality(String),
    state              LowCardinality(String),
    dept_id            UInt16,
    dept_name          LowCardinality(String),
    consulting_doctor  LowCardinality(String),
    visit_type         LowCardinality(String),
    priority           LowCardinality(String),
    payment_mode       LowCardinality(String),
    is_insured         UInt8,
    coverage_type      LowCardinality(String),
    registration_fee   Decimal(10, 2),
    chief_complaint    String,
    chronic_conditions String,
    -- ... any other report column, all flat
    version            UInt64,                      -- from the event; highest wins
    is_deleted         UInt8,
    ingested_at        DateTime DEFAULT now(),
    INDEX idx_name patient_name TYPE ngrambf_v1(3, 65536, 3, 0) GRANULARITY 4   -- fast "contains" search
)
ENGINE = ReplacingMergeTree(version, is_deleted)
PARTITION BY toYYYYMM(registration_date)
ORDER BY (registration_date, dept_id, patient_id);

Why this shape

One flat row per patient means no joins at query time. LowCardinality dictionary-encodes repeating values. Monthly partitions make date filters skip whole months. Sorting by date and department makes the most common filters read only the relevant blocks.

Updates and deletes

ReplacingMergeTree keeps the latest version of each patient and drops deleted ones during background merges. Queries that must be exact use FINAL (or argMax); recent ClickHouse versions make FINAL efficient.

Example report queries

-- Report 2 (department summary) on any period: one pass over 3-4 columns
SELECT dept_name, count() AS total, countIf(gender = 'Male') AS male, countIf(gender = 'Female') AS female,
       countIf(is_insured = 1) AS insured, round(avg(age_years), 1) AS avg_age, sum(registration_fee) AS fee
FROM patient_report FINAL
WHERE registration_date BETWEEN '2026-01-01' AND '2026-09-30' AND is_deleted = 0
GROUP BY dept_name ORDER BY dept_name;

-- Column-level filter on any column, no extra index needed
SELECT registration_no, patient_name, city, dept_name
FROM patient_report FINAL
WHERE state = 'Maharashtra' AND chronic_conditions LIKE '%Diabetes%' AND age_band = '60+'
ORDER BY registration_date DESC LIMIT 50;

Aggregate tables for dashboards can be added as refreshable materialized views. Insert-triggered aggregate views would double-count updated patients, so they are avoided for data that can change.

10.Protecting the live database

  • Change-log retention cap: if Debezium stops, its replication slot makes PostgreSQL keep the change log, which can fill the disk. Set max_slot_wal_keep_size to cap it, and alert on slot lag. If the cap is hit, the slot is invalidated and the read side is re-synced by backfill, so the live database is never put at risk.
  • Minimal publication: publish only the outbox table, so Debezium reads only the changes it needs.
  • Backfill off-hours, in monthly chunks, preferably from a read replica.
  • Guard rails for any report still on PostgreSQL: a separate database role with statement_timeout and a connection limit; the download limit already in the POC.
  • Guard rails in ClickHouse: per-user settings profiles and quotas (max_execution_time, max_memory_usage, concurrent-query limits), so one heavy report can't starve other report users either.

11.Security & compliance

Patient records are sensitive personal data (for example under India's Digital Personal Data Protection Act, 2023). Copying them to a second store increases exposure, so the design keeps that copy as small and as controlled as possible:

  • Data minimisation: the outbox payload contains only report fields; no Aadhaar, masked mobile numbers, and no free-text medical notes unless a report really needs them.
  • Access control: separate ClickHouse users per application and role; row policies (for example, a department head sees only their department); read-only reporting users.
  • Kafka: topics restricted to the pipeline's service accounts, with short retention (for example 7 days), since ClickHouse holds the long-term copy.
  • Encryption and audit: TLS between components in production; disk encryption on servers; ClickHouse's query_log records who ran what.
  • Retention: ClickHouse TTL rules can drop or anonymise data older than the agreed retention period automatically.

15.Rollout to the live product (after a successful POC)

  1. Shadow mode: run the pipeline in production with no user-facing change; reconciliation runs nightly.
  2. New reports first: release only the new /analytics reports and background exports.
  3. Switch old reports one at a time via the per-report setting, starting with the heaviest. Rollback is flipping the setting back.
  4. Retire PostgreSQL-side report queries once all reports have moved, which removes the remaining report load from the live database.
  5. Production hardening: ClickHouse replication (2 replicas), a 3-broker Kafka, monitoring of lag, slot size and query times, backups of ClickHouse.

17.Decisions needed before starting

  1. Direction: go with the recommended CDC → ClickHouse design, or start smaller with a read replica only?
  2. Flattening approach: the outbox (one small change in the save code, seconds-fresh flat table) or table-level CDC with no save-path change (more ClickHouse work, minutes-fresh)?
  3. New reports for the POC: which 3–4 reports or column filters matter most for the live product?
  4. POC data size: 50 lakh or 1 crore (the latter needs Docker's disk moved to D:)?
  5. Permissions on this machine: OK to set wal_level=logical and restart the Postgres container, add containers, and raise the Docker/WSL memory limit?
